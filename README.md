# Service Desk

Веб-приложение для внутренней обработки заявок в компании: инциденты, сервисные запросы, согласования, работа специалистов по группам и базовый SLA.

## Что уже есть в проекте

- каталог услуг с древовидной структурой;
- создание заявок через главную страницу;
- роли `user`, `specialist`, `manager`, `admin`;
- очередь заявок для специалистов;
- канбан;
- карточка заявки с комментариями, историей, SLA и согласованием;
- уведомления в шапке;
- админка пользователей, каталога и рабочих групп;
- согласование заявок руководителем.

## Технологии

- Backend: Python 3.10+, Flask, Flask-Login, Flask-SQLAlchemy
- Frontend: Jinja2, HTML, CSS, Vanilla JavaScript
- База данных: PostgreSQL
- ORM: SQLAlchemy

## Быстрый запуск

### 1. Создать виртуальное окружение

```bash
python -m venv venv
```

Активация:

- Windows: `venv\Scripts\activate`
- Linux/macOS: `source venv/bin/activate`

### 2. Установить зависимости

```bash
pip install -r requirements.txt
```

### 3. Подготовить PostgreSQL

Создать пользователя и базу:

```sql
CREATE USER service_desk_user WITH PASSWORD 'service123';
CREATE DATABASE service_desk_db OWNER service_desk_user;
GRANT ALL PRIVILEGES ON DATABASE service_desk_db TO service_desk_user;
```

### 4. Применить SQL-скрипты

```bash
psql -U service_desk_user -d service_desk_db -f sql/01_schema.sql
psql -U service_desk_user -d service_desk_db -f sql/02_functions.sql
```

`sql/03_cleanup.sql` нужен только если поднимаете проект на старой базе и хотите удалить старые неиспользуемые таблицы.

### 5. Проверить подключение к БД

Параметры лежат в `app.py` в `DB_CONFIG`:

```python
DB_CONFIG = {
    "user": "service_desk_user",
    "password": "service123",
    "host": "127.0.0.1",
    "port": "5432",
    "database": "service_desk_db",
}
```

### 6. Инициализировать систему

```bash
flask --app app init-db
```

Команда:

- создаёт недостающие таблицы;
- дотягивает старую схему, если база отстаёт;
- создаёт базовые рабочие группы;
- создаёт стартовые SLA;
- создаёт администратора по умолчанию.

Стартовый админ:

- логин: `admin`
- пароль: `Admin123!`

### 7. Запустить приложение

```bash
python app.py
```

После запуска приложение будет доступно по адресу:

`http://127.0.0.1:5000`

## Основные роли

### user

- создаёт заявки;
- видит свои заявки;
- комментирует свои обращения;
- работает через главную страницу и профиль.

### specialist

- видит очередь заявок и канбан;
- работает с заявками своей рабочей группы;
- может брать заявку в работу;
- при переводе свободной заявки в `В работе` становится исполнителем автоматически.

### manager

- делает всё, что может specialist;
- может назначать исполнителя;
- участвует в согласовании как руководитель.

### admin

- полный доступ ко всей системе;
- управляет пользователями, каталогом и рабочими группами.

## Основные разделы

### Главная

- дерево каталога услуг;
- создание заявки из кнопки или сразу по клику на услугу;
- список своих заявок;
- поиск.

### Заявки

- таблица очереди специалистов;
- фильтры;
- назначение исполнителя;
- быстрая смена статуса.

### Канбан

- карточки-счётчики;
- канбан по статусам;
- группировка карточек по родительской услуге;
- внутри карточки видно услугу, автора, исполнителя, дедлайн и просрочку.

### Согласование

- заявки, требующие решения;
- мои заявки в ожидании;
- история согласований;
- переход из строки сразу в карточку заявки.

### Карточка заявки

- большая карточка с основными данными;
- SLA и сроки;
- история изменений;
- комментарии;
- блок согласования;
- рабочая форма изменения статуса и исполнителя.

### Админка

- пользователи;
- сброс пароля через модальное окно;
- каталог услуг;
- рабочие группы.

## Схема базы данных

Основные таблицы в схеме `sm`:

- `users` — пользователи;
- `passwords` — хэши паролей и флаги первого входа;
- `user_roles` — роли;
- `work_groups` — рабочие группы;
- `user_work_groups` — связь пользователей и групп;
- `sla_policies` — SLA-политики;
- `service_catalog` — каталог услуг и категорий;
- `tickets` — заявки;
- `ticket_history` — история изменений;
- `ticket_param_values` — комментарии и служебные значения;
- `ticket_approvals` — шаги согласования по заявке;
- `notifications` — уведомления.

## SLA и статусы

Система поддерживает:

- срок первой реакции;
- срок решения;
- просрочку по дедлайну;
- отображение SLA в карточке заявки и на канбане.

Основные рабочие статусы:

- `new`
- `assigned`
- `in_progress`
- `pending_approval`
- `resolved`
- `closed`
- `cancelled`
- `rejected`

## Полезные замечания

- В проекте много логики завязано на рабочие группы, поэтому для специалистов и менеджеров важно корректно назначать `work_group_uid`.
- Если заявка требует согласования, обычное обновление карточки блокируется до решения согласующего.
- Часть логики старых учебных баз всё ещё поддерживается через `init-db`, чтобы не падать на старой схеме.
